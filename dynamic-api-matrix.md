## 读法与限制

- “动态已观察”只证明该网络调用在窗口内出现；不证明由哪次人工操作触发。
- protobuf 字段名由动态 top-level field number 与静态 Proto 对齐；gzip 响应未由采集器解压时，只能引用静态响应 schema。
- `SendGrokBotUserMessage`、`SyncOnePasswordConnections`、`RegisterSandMachine` 均在窗口中真实出现，是写调用；内容与触发者未知。
- `forum.cursor.com` GET 比 `SendGrokBotUserMessage` 请求早约 34.0 秒；时间上先后成立，但没有 request ID、trace 或代码路径证据可建立因果关系。
- api2 上的 Analytics/BackgroundComposer 作为明确共用能力保留；其他无关 Cursor 通用流量不用于推导 GrokBot 业务架构。

## 关键动态结论

- ConnectRPC 实际同时使用 HTTP/1.1 与 HTTP/2；Unary 为 `application/proto`，server stream 为 `application/connect+proto`。
- Box Gateway 的 `/health`、`/events`、`/api/*`、Cookie origin approval 与 WebAuthn request channel 均真实出现，证明“中央控制面 + Box-scoped Gateway”双层 API；动态流量不能确定 Gateway 进程的物理部署位置。
- `SendGrokBotUserMessage` 返回 200，证明窗口内确有消息写入；不能从脱敏抓包得出消息内容、发起人或最终执行结果。
- `SyncOnePasswordConnections` 与 `RegisterSandMachine` 证明凭证目录同步、机器注册确实会发写请求；不能据此判断是谁或哪项 UI 操作触发。
- 未观察到 Appium、模拟器池或云真机 farm 调度协议；当前证据支持的是持久 Linux Box + VNC，以及用户本机 Local Exec Relay。
